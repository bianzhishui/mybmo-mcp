# 项目上下文

## 目的

mybmo-mcp 把百度营销开放平台的账户、关键词、投放与报表能力封装成 MCP 工具，
让 AI 客户端可以在**多账户、有权限边界**的前提下读取投放数据、生成改动物料。

核心价值不在"多包一层 API"，而在两件百度原生不支持的事：

1. **接口全量可达、上下文恒定**：SDK 支持的接口全部可调用，工具定义不随接口数量增长。
2. **多账户统一入口**：一套服务管 N 个百度账户，令牌隔离、别名可控、不会串号。

**本服务不承担业务编排与写审批**——拓词、报表汇总、写前确认属于调用方（skill 工作流）的职责，
见 [ADR 0003](../docs/decisions/0003-capability-only.md)。

## 技术栈

| 组件 | 选择 | 版本约束 |

| 语言 | Python | 3.12（`requires-python = ">=3.12"`） |

## 项目约定

### 代码风格

- `ruff` 统一格式化与 lint，行宽 100
- 全部公开函数带类型注解；`from __future__ import annotations` 按 ruff 规则决定
- 异常用自定义类型，不用裸 `Exception`；错误信息面向用户可读，不暴露内部路径

### 架构模式

- **传输层与业务层分离**：`baidu/transport.py` 只管 HTTP、重试、错误归一化；
  `baidu/services/*` 只管业务语义
- **工具薄、服务厚**：MCP 工具函数只做参数校验与结果渲染，逻辑落在 services
- **凭据不进工具层**：工具拿到的永远是"已鉴权的 client"，不是令牌字符串

### 测试策略

- 默认**不打真实百度接口**，全部用脱敏 fixture
- 需要真实账户的用例打 `@pytest.mark.live`，CI 默认跳过
- 关键回归必须覆盖：令牌刷新轮换、跨账户越权（alias 不在授权列表时被拒）
- 禁止在测试中写入真实凭据目录

### Git 工作流

- 主干 `main`，功能分支 `feat/<topic>`、修复 `fix/<topic>`
- 提交信息用祈使句，前缀 `feat:` / `fix:` / `docs:` / `test:` / `chore:`
- 不提交 `.env`、凭据文件、真实账户数据

## 领域上下文

### 百度营销接口的三条硬规则

1. **请求头在 body 里**：`header.userName`、`header.accessToken`、`header.action`
   是 JSON 请求体的一部分，不是 HTTP 头。
2. **`userName` 必须是令牌所属账户的中文名**，填错报 `81020`。
   这就是为什么授权回调后必须先调 `getUserInfo` 落库账户名。
3. **服务名/方法名大小写敏感**：`getKRByQuery` 不是 `getKRbyQuery` 之外的任何变体，
   网关大小写归一化会直接 404（`87091 request url is invalid`）。

### 令牌模型

| 令牌 | 有效期 | 特性 |
|---|---|---|
| accessToken | ~24h | 随请求发送 |
| refreshToken | ~30d | **刷新会轮换**，旧值立即失效 |

轮换意味着并发刷新必须加锁：两个请求同时刷新，后到的会拿到失效令牌，账户直接掉线。

### 权限模型

百度权限是「应用 + 账户」双维度的，不是全局的。
MCP 侧无法替用户补权限，只能如实报告"该应用在该账户上没有此权限"。

## 重要约束

- **不得生成演示数据**：没有凭据就明确说不能取数，返回结构化提示，不返回假数字。
- **写操作不自动重试**：超时属于"结果未知"，必须先查后写。
- **百度令牌永不离开服务端**：不进日志、不进 MCP 响应、不进模型上下文。
- **模型不决定账户**：账户只能从服务端返回的授权列表里选，且必须经过归属校验。
- **默认最小权限**：新绑定账户默认只读，写权限需显式授予。
