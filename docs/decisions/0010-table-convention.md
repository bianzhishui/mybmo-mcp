# ADR 0010：PostgreSQL 表规范

- 状态：已接受
- 日期：2026-11-12
- 决策者：项目负责人
- 关联：[ADR 0004](0004-multi-tenant-accounts.md)、[ADR 0007](0007-credentials-in-postgres.md)、
  [ADR 0009](0009-postgres-only.md)

## 背景

ADR 0009 之后运行期只剩 PostgreSQL，库里已经有 9 张表。它们的建表方式不统一：

- `account_grants` / `credentials` / `app_secrets` / `binding_states` 用**复合主键**，
  没有 `id`
- `tenants` / `users` 只有 `created_at`，没有 `updated_at`
- `audit_log` / `subscribe_events` 有 `id` 但没有 `created_at` / `updated_at`
- 业务时间列各叫各的（`issued_at` / `received_at` / `started_at`）

排查问题、写运维脚本、做增量同步时，每张表都要重新看一眼结构。规范化的收益
主要是**降低认知成本**，而不是性能。

## 决策

### D1 每张业务表：`id` 第一列，`bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY`

- 统一自增代理键：不需要应用生成、天然唯一、索引局部性好
- 用 `GENERATED ALWAYS` 而不是 `BY DEFAULT`：**禁止应用显式写 id**，
  避免"有人传了 id 就冲突"这类事故（回灌历史数据时用 `OVERRIDING SYSTEM VALUE`）

### D2 最后两列固定 `created_at` / `updated_at`

`timestamptz NOT NULL DEFAULT now()`。`updated_at` 由触发器 `set_updated_at()`
（`BEFORE UPDATE`）自动维护：

- 不靠应用记得写——新增代码路径不会漏
- 应用里已有的显式 `SET updated_at = now()` 保留（幂等，不冲突）

### D3 代理键 vs 自然键：数字 id 不进业务层

`tenants` 增加 `tenant_key text UNIQUE`（值就是原来的 `"t_default"`），
其余表的 `tenant_id` 列**保持 text** 并外键指向 `tenants(tenant_key)`。

理由：日志、审计、CLI 里需要可读的租户标识；把数字 id 暴露到业务层会污染
`audit_log.tenant_id`、`binding_states.tenant_id` 等一串列，并让排查变成查表。

其余表的自然键本来就存在，只是从"主键"降级为"唯一约束"：
`users(tenant_id, idp_subject)`、`baidu_accounts(tenant_id, alias)`、
`credentials(tenant_id, alias)`、`app_secrets(tenant_id, app_id)`、
`account_grants(user_id, account_id)`、`binding_states(nonce)`、`audit_log(call_id)`。

> `ON CONFLICT` 依赖的是**唯一约束**而不是主键，所以改主键不需要改 SQL。

### D4 业务时间列合并

| 表 | 处理 |
|---|---|
| `binding_states.issued_at` | 并入 `created_at`（同一时刻） |
| `subscribe_events.received_at` | 并入 `created_at`（同一时刻） |
| `audit_log.started_at` / `finished_at` | **保留**（调用起止，语义不同），另加两列记账 |

### D5 `schema_version` 豁免

它是迁移账本：`version` 就是主键，`applied_at` 就是时间，加 `id` 会破坏
"版本号唯一"的直觉，也让迁移器多一次往返。

### D6 时区：所有时间按 `Asia/Shanghai` 显示

`timestamptz` 存 UTC，显示取决于会话时区。三处一起设：

- 数据库：`ALTER DATABASE <db> SET timezone = 'Asia/Shanghai'`（迁移 008）
- 容器：compose 里 `TZ: Asia/Shanghai`（日志时间戳）
- 代码：审计返回的 `datetime.isoformat()` 自动带 `+08:00`

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 保留复合主键，只加 `created_at`/`updated_at` | 排查时每张表结构不同，规范的意义就没了 |
| `id uuid DEFAULT gen_random_uuid()` | 用户明确要求统一 bigint identity；且日志表量大时 uuid 索引更臃肿 |
| `GENERATED BY DEFAULT` | 允许应用写 id，等于留了个"传错就冲突"的口子 |
| 只 ALTER 加列、不重建 | Postgres 不能调列序，`id` 会排到最后，规范形同虚设 |
| `tenant_id` 全链路改 bigint | 数字 id 会污染日志/审计/CLI，改动约 40 处 |

## 后果

### 正面

- 任何一张表结构一眼可预期：`id` 在最前、时间在最后
- `updated_at` 不再依赖应用自觉
- 新增表有护栏：`tests/test_schema_convention.py` 内省校验，违规直接红

### 负面 / 需要承担

| 风险 | 应对 |
|---|---|
| 重建表有停机/数据风险 | 单事务迁移 + 事前 `pg_dump`；当前数据量 < 20 行 |
| 代理键与自然键并存，容易混用 | 约定：**跨表引用用自然键，id 只做行标识**；FK 已按此建 |
| 触发器是隐式行为 | 迁移里显式建触发器，规范测试校验"每张表都有" |
| 历史 id（uuid）丢失 | `users` / `baidu_accounts` 的旧 uuid 不再保留；外部没有引用它们（审计用的是 sub/alias） |

## 新增表的 checklist

1. 第一列 `id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY`
2. 业务列（含 `tenant_id text REFERENCES tenants(tenant_key)`）
3. 自然键 `UNIQUE` 约束
4. `created_at` / `updated_at` 作为最后两列
5. `CREATE TRIGGER trg_<表>_updated_at BEFORE UPDATE ... EXECUTE FUNCTION set_updated_at()`
6. 跑 `tests/test_schema_convention.py`，绿了才算完
