# ADR 0001：公网接入鉴权采用自部署 Casdoor

- 状态：已接受
- 日期：2026-11-07
- 决策者：项目负责人

## 背景

mybmo-mcp 需要放在公网，供 MCP 客户端（Claude Desktop、Cursor、VS Code 等）接入。
这带来一个与传统 Web 应用不同的问题：**客户端是用户临时填一个 URL 接入的，此前从未与我们的授权服务器建立过关系**，
所以无法预分配 client_id。

同时，百度营销的 accessToken 是**发给百度 API 的**，受众不是我们的服务。
如果把它直接当 MCP 的 Bearer 令牌，会同时违反两件事：

1. MCP 规范要求校验 token audience
2. 百度令牌泄露面扩大（它会被写进客户端配置、日志、模型上下文）

因此必须引入一个独立的授权服务器，签发**只对我们的服务有效**的令牌。

## 决策

**自部署 Casdoor 作为 OAuth 2.1 授权服务器；mybmo-mcp 作为 Resource Server 校验其 JWT。**

采用单机部署：腾讯云轻量 2核2G（¥45/月），Casdoor + mybmo-mcp + PostgreSQL 同机，
Caddy 做反向代理与自动证书，管理台不暴露公网。

## 备选方案对比

| 方案 | 成本 | MCP 适配 | 否决理由 |
|---|---|---|---|
| **Casdoor 自部署** | ¥45/月 | DCR + CIMD + RFC 8707 + 工具级权限 | **采纳** |
| Logto 自部署 | ¥100/月（需 2C4G） | 仅 CIMD，**不支持 RFC 7591 DCR** | 老客户端接不进来；强制 PostgreSQL |
| Keycloak 自部署 | ¥100/月（JVM，≥2G） | DCR 端点无 CORS | 大多数 MCP 客户端无法自助注册；运维重 |
| Tencent OneID | 按 MAU 询价 | 未验证 | 面向企业 CIAM 定价，规模不匹配 |
| 腾讯云 AI Agent 安全网关 | ~¥6000/月 | 是网关非授权服务器 | 价格与需求严重不匹配 |
| Auth0 / Logto Cloud | 免费额度足够 | 好 | 数据出境；且免费额度政策会变 |
| 静态 Bearer Token | ¥0 | 客户端可配 header | 不能自助接入、无法多租户、泄露后需人工轮换 |

## 理由

1. **同时支持 DCR 与 CIMD**。新客户端走 CIMD，老客户端走 RFC 7591，覆盖面无短板。
   Logto 缺 DCR 是硬伤——用户用一个还在走 DCR 的客户端就完全接不进来。
2. **资源占用最低**。Go 单二进制，SQLite 可起步，2核2G 能同时跑三个服务。
   Logto 必须 PostgreSQL，2核2G 很紧；Keycloak 是 JVM，2G 起步。
3. **MCP 能力是原生的**，不是拼出来的：内置 MCP Server、工具级权限、resource indicator、DPoP。
4. **协议面留了退路**。SAML / CAS / LDAP / RADIUS / SCIM 都在。
   如果以后要对接广告主的企业 AD 或做员工 SSO，不用换系统。
5. **许可宽松**。Apache-2.0，改造后不必开源。
6. **中文文档与国内实践**，出问题能查得到。

## 后果

### 正面

- 接入鉴权与百度鉴权彻底解耦，令牌不再混用
- 新增用户零人工：贴 URL → 自助注册 → 登录 → 授权
- 成本固定，不按人头涨

### 负面 / 需要承担

| 风险 | 说明 | 缓解 |
|---|---|---|
| 自运维 | 认证服务挂了，所有调用都进不来 | 独立备份、监控、不和生产业务挤机器 |
| CIMD 较新 | 2026-10 才上线，实战样本少 | 保留 DCR 作为主路径，CIMD 为增强 |
| DCR 默认关闭且无鉴权 | 开启后任何人可注册应用 | 按组织开启 + 回调 URI 白名单 + 注册频率限制 |
| 默认口令 | 初始 `admin/123` | 部署脚本强制修改 |
| issuer 不可变 | 域名写进 token | **第一天上生产域名**，禁止先用 IP 后换域名 |
| 单维护团队 | 迭代快、版本变更需读 changelog | 锁定小版本，升级前在预发验证 |

## 未决问题

- [ ] Casdoor 的 `dcrPolicy` 是否支持按来源 IP / 网段限制注册
- [ ] 多租户映射：Casdoor Organization ↔ 本项目 `tenant` 一对一，还是复用单一组织靠 `account_grants` 区分
- [ ] Casdoor 升级路径与数据迁移策略
- [ ] 是否需要 token exchange（RFC 8693）支持"代理代表用户"的链式调用

## 附：为什么不用"我们自己签发令牌"

自己实现 OAuth 授权服务器意味着自己处理 PKCE、授权码一次性、state 防重放、
令牌签名与轮换、JWKS 发布、同意页、客户端注册策略。
这部分**没有任何业务价值**，出错代价却极高（等于把账户体系交给未审计代码）。
用成熟实现，把精力放在百度接口与多账户隔离上。
