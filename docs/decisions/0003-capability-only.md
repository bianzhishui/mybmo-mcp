# ADR 0003：定位收缩为「能力层」，不做业务编排与写审批

- 状态：已接受
- 日期：2026-11-07
- 决策者：项目负责人
- 取代：[design.md](../../openspec/changes/bootstrap-mcp-server/design.md) 的 D1（不用 SDK）、D2（业务闭环粒度）、D3（审批）
- 不影响：[ADR 0002](0002-tech-stack.md) 的框架选型（`mcp` / `httpx2` / PG / Caddy 仍然有效）

## 背景

项目最初按「业务闭环」设计：10 个左右的工具，`keyword_plan`、`account_snapshot`、
`query_report`，写操作走 `change_preview → 确认 → change_execute`。

重新对齐目标后，需求是两件事：

1. 把 `baiduads-sdk` 支持的**全部接口**包一层，供 agent 调用
2. 加鉴权与多账户：多用户使用，每个用户可关联多个百度账户

业务编排（拓词、报表汇总、写前确认）属于 **skill 的工作流层**，
不属于 MCP 服务的能力层。把两者混在一起，会导致能力层被具体业务绑死：
每加一个业务场景就要改一次服务，而 399 个接口里绝大多数永远等不到专用工具。

## 决策

**MCP 只提供「能力」与「账户」两件事。**

常驻工具 5 个：

| 类型 | 工具 | 职责 |
|---|---|---|
| 能力 | `search_capabilities` | 按中文/英文关键词检索能力 |
| 能力 | `get_capability_schema` | 取某个能力的完整参数定义 |
| 能力 | `execute_capability` | 忠实执行，**不做写操作拦截** |
| 账户 | `list_accounts` | 当前用户可访问的百度账户 |
| 账户 | `auth_status` | 令牌状态与有效期 |

配套决定：

- **执行层直接用 `baiduads-sdk`**（反转 ADR 0002 的 D1）。它的依赖只有
  `urllib3>=1.25.3` + `python-dateutil`，没有锁旧版 urllib3，此前的否决理由不成立
- **不做写操作拦截**。`mutating` 作为能力元数据对外暴露，是否确认由调用方决定
- **不做业务组合**。`account_snapshot`、`keyword_plan`、`query_report` 移出本服务
- 内部仍保留读写判定，但**只用于重试策略**（写请求不重发），不用作审批依据

## 备选方案对比

| 方案 | 常驻工具 | 上下文成本 | 覆盖 | 否决/采纳理由 |
|---|---|---|---|---|
| 全量注册 | 399 | 5–8 万 tokens | 全部 | 客户端扛不住，选择准确率崩 |
| 按服务分组 | 129 | 2–3 万 tokens | 全部 | 只压缩名字空间，`body` 仍自由；且丢失组合语义与工具级只读标注 |
| curated + 透传 | 10 | 约 2 千 tokens | 全部 | 需要维护白名单，长尾两跳 |
| **检索式网关** | **5** | **约 800 tokens** | **全部** | **采纳**：O(1) 成本，能力增长不增加工具数 |
| 多开 MCP 服务按域拆 | 各自 10–30 | 总量不降 | 全部 | 客户端同时挂载时总量反而上升；鉴权/审批需重复实现 |

## 理由

**一、工具定义成本与接口数量解耦。** 399 个接口的说明不可能都塞进常驻上下文，
但检索式下只有 `search_capabilities` 的返回值随目录增长，工具定义恒定。
这也让"每个接口写完整描述"从奢侈变成可行——描述只在用到时取。

**二、职责边界清晰。** MCP 回答"这个能力叫什么、参数是什么、怎么执行"；
skill 回答"什么时候该用、要不要先问用户"。两边可以独立演进。

**三、能力层可以只做一件事，做扎实。** 参数校验、错误归一化、令牌刷新、多账户隔离——
这些做好已经足够；业务组合每加一个都要重新设计字段映射，收益却只服务一个场景。

## 后果

### 正面

- 接口全量可达，且工具列表恒定
- 新增接口（2023 之后百度加的）只需追加能力条目，不改工具
- 删除约 500 行业务组合代码，概念更少
- 未来接第二个广告平台时，同一套 5 个工具可复用

### 负面 / 需要承担

| 风险 | 说明 | 应对 |
|---|---|---|
| 长尾调用三跳 | search → schema → execute，每次多 1–2 轮推理 | 高频能力可后续提升为直连工具（保留扩展位） |
| 检索质量决定可用性 | 默认子串匹配在中文下不可用 | 必须做中文别名词典 + BM25，不能只靠子串 |
| 无写拦截 | 误调 `deleteCampaign` 不可逆 | 在能力元数据标 `destructive`，由 skill 层提示；生产可配只读模式 |
| 越权风险上升 | 没有审批兜底后，账户归属成为唯一防线 | `sub → account_grants` 校验必须做，且优先级前移 |
| SDK 停在 2023.1.0 | 新接口没有对应模型 | 保留 `transport.py` 作为裸调 fallback |

## 未决问题

- [ ] SDK 在 Python 3.12 上的导入与序列化 POC（不通过则整个执行层回退到 `transport.py`）
- [ ] `mutating` 判定标准：SDK wrapper 类名前缀 + 动名词表，灰区标 `unknown` 待人工裁决
- [ ] 账户归属：用户私有 vs 租户共享（当前按「用户私有 + 预留 tenant_id」实现）
- [ ] 中文检索是走别名词典 + BM25，还是引入全文检索扩展
